# Binding the C ABI

`core/include/dhow.h` is generated by cbindgen from the Rust source and
committed, so a caller can build against it without a Rust toolchain. This is
how to use it from something that is not Go.

The Go bindings in [`cli/internal/ffi`](../cli/internal/ffi) are the worked
example. Everything below is visible there in a form that compiles.

## Building the library

```bash
cd core && cargo build --release -p dhow-ffi
```

Produces `core/target/release/`:

| Artifact | Use |
|----------|-----|
| `libdhow_ffi.a` | static archive — what a release links |
| `libdhow_ffi.dylib` / `.so` | dynamic library — convenient for development |

**Link the archive for anything you ship.** Both land in the same directory and
most linkers prefer the dynamic one given `-ldhow_ffi`, which produces a binary
that references the library by its absolute build path and starts on exactly one
machine. That is not hypothetical — it is what dhow's own release build did
until [Phase 33](phase-log.md) measured it.

## The rules

Three, and each has a reason worth knowing before you rely on it.

### 1. Handles are opaque

The header declares incomplete struct types. `DhowKey`, `DhowIdentity`,
`DhowPublicIdentity`, `DhowEncoder`, `DhowDecoder`, `DhowManifest`, and
`DhowHasher` have no visible layout, so nothing you write can depend on one.

Every `*_new`, `*_generate`, `*_load`, `*_build`, or `*_verify` returns a handle
you own. Release it with the matching `*_free`. **Passing NULL to any `_free` is
a no-op**, so a cleanup path needs no null check. Using a handle after freeing
it is undefined behaviour, as with any C API.

### 2. Buffers are caller-allocated

This library never returns a pointer you must free. That removes the class of
bug where two allocators disagree about a block of memory, and it means you can
use whatever allocator you like.

Anything variable-length follows one convention:

```c
size_t needed = 0;
if (dhow_manifest_bytes(m, NULL, 0, &needed) != DHOW_STATUS_OK) { /* handle */ }

uint8_t *buf = malloc(needed);
if (dhow_manifest_bytes(m, buf, needed, NULL) != DHOW_STATUS_OK) { /* handle */ }
```

Call with a NULL buffer to learn the size, then call again. A buffer that is one
byte short returns `DHOW_STATUS_BUFFER_TOO_SMALL` and **writes nothing** — it
does not truncate.

### 3. No raw key material in any signature

There is no function that takes or returns key bytes. Keys exist as handles, and
the only ways to get one are `dhow_key_generate`, `dhow_key_load`,
`dhow_identity_generate`, `dhow_identity_load`, and `dhow_public_load`.

If you find yourself wanting to pass a key as a `const uint8_t *`, the answer is
that you cannot, and that is the point. The derived session key never crosses the
boundary at all.

## Errors

Every function returns `DhowStatus` — zero for success, negative for failure — or
a handle that is NULL on failure.

```c
DhowEncoder *enc = dhow_encoder_new(key, sid, salt, nonce, params, payload, len);
if (enc == NULL) {
    size_t needed = dhow_last_error_message(NULL, 0);
    char *msg = malloc(needed);
    dhow_last_error_message(msg, needed);
    fprintf(stderr, "dhow: %s\n", msg);
    free(msg);
}
```

`dhow_last_error_message` describes the most recent failure **on the calling
thread**. The storage is thread-local, so a thread that did not make the failing
call sees nothing useful. If your runtime can move a task between OS threads,
pin it for the duration of any call whose error you intend to read — this is
exactly what the Go bindings do with `runtime.LockOSThread`.

Error strings never contain payload bytes or key material. That is a property the
core is written to hold and
[tested](THREAT-MODEL.md#keys), which is what makes them safe to log.

### Status codes

| Code | Meaning |
|------|---------|
| `0` | success |
| `-1` | a required pointer was NULL |
| `-2` | an argument was out of range |
| `-3` | a buffer was too small; nothing was written |
| `-4` | the session parameters were rejected |
| `-5` | a frame failed parsing, authentication, or integrity |
| `-6` | the decoder does not yet hold enough symbols |
| `-7` | a digest, MAC, or signature check failed |
| `-8` | encryption or decryption failed |
| `-9` | key generation, loading, or storage failed |
| `-10` | an internal error |
| `-11` | **a panic was caught at the boundary — always a bug in this library** |
| `-12` | a resume state was malformed or did not match its journal |

`-6` is the one a caller routinely branches on rather than treating as failure:
a receiver polls until the transfer completes.

`-11` should never happen. Every entry point runs inside a `catch_unwind`,
because unwinding across a C ABI is undefined behaviour; seeing this code means
the guard did its job and there is a defect to report. The panic message is
deliberately **not** forwarded, because a panic payload can contain interpolated
values from the data path.

## Checking the version

```c
if (dhow_abi_version() != DHOW_ABI_VERSION) {
    fprintf(stderr, "dhow: built against ABI %u, linked against %u\n",
            DHOW_ABI_VERSION, dhow_abi_version());
    return 1;
}
```

`DHOW_ABI_VERSION` is a macro in the header, fixed when you compiled;
`dhow_abi_version()` is what the linked library actually is. Refuse to run on a
mismatch rather than guessing at a handle's layout. The version is bumped on any
incompatible change to the C surface — it is **4** as of the manifest work in
Phase 28.

## Sending

```c
DhowKey *key = dhow_key_load("operator.key");
DhowIdentity *identity = dhow_identity_load("sender.key");

DhowSessionParams params = {
    .payload_size = plaintext_len,   /* recomputed from the ciphertext */
    .block_count = 8,
    .symbol_size = 1320,
    .source_symbols_per_block = k,
    .total_symbols_per_block = k + repair,
    .payload_digest = {0},           /* recomputed */
};

DhowEncoder *enc = dhow_encoder_new(key, session_id, salt, nonce,
                                    params, plaintext, plaintext_len);

/* The encoder recomputes payload_size and payload_digest over the
   *ciphertext*, which is longer by the AEAD tag. Read them back rather than
   reimplementing the rule; they are what must travel in the manifest. */
DhowSessionParams resolved;
dhow_encoder_params(enc, &resolved);

int count = dhow_encoder_frame_count(enc);
for (int i = 0; i < count; i++) {
    size_t needed = 0;
    dhow_encoder_frame(enc, i, NULL, 0, &needed);
    uint8_t *frame = malloc(needed);
    dhow_encoder_frame(enc, i, frame, needed, NULL);
    /* render or write it */
    free(frame);
}
```

The encoder holds every frame, so frames can be served in any order and as many
times as needed — which is what an unacknowledged optical channel requires: the
sender cannot know which frames the camera caught.

## The manifest inventory across the ABI

The awkward part of this boundary. The inventory is variable-length in two
dimensions: a variable number of entries, each with a variable-length name.

**Going in**, compose an array and pass a pointer and a count. Names are borrowed
for the duration of the call and nothing is retained, so they must outlive it —
and no longer:

```c
DhowFileEntry entries[2] = {
    { .name = "docs/readme.md", .size = 100, .digest = {...},
      .executable = 0, .reserved = {0} },
    { .name = "run.sh", .size = 12, .digest = {...},
      .executable = 1, .reserved = {0} },
};

DhowManifest *m = dhow_manifest_build(identity, session_id, salt, nonce,
                                      resolved, entries, 2);
```

`reserved` **must be zero**. A non-zero byte is rejected rather than ignored,
because it means either a newer header than this library or an uninitialised
struct, and both are worth refusing.

**Coming out**, there is no array. A verified manifest is a handle and its
entries are read one at a time:

```c
int n = dhow_manifest_file_count(m);
for (int i = 0; i < n; i++) {
    size_t needed = 0;
    dhow_manifest_file_name(m, i, NULL, 0, &needed);
    char *name = malloc(needed + 1);
    dhow_manifest_file_name(m, i, (uint8_t *)name, needed, NULL);
    name[needed] = '\0';           /* the name is NOT NUL-terminated */

    uint64_t size; dhow_manifest_file_size(m, i, &size);
    int exec = dhow_manifest_file_executable(m, i);
    free(name);
}
```

Handing back an array would mean handing back allocations you must free with an
allocator this library does not own, which is the one thing rule 2 forbids.

## Verifying

```c
DhowPublicIdentity *signer = dhow_public_load("sender.pub");

/* NULL session id: you have nothing to bind to yet, which is the ordinary case.
   The manifest is what tells you which session this is. */
DhowManifest *m = dhow_manifest_verify(signer, bytes, len, NULL);
if (m == NULL) { /* it did not verify. Stop. */ }
```

A `DhowManifest` can only be produced by building one from an identity or
verifying one against a public identity. **There is no way to obtain one by
parsing**, so holding the handle means the signature was checked.

Pass a non-NULL session id when you already know which session you are receiving
— resumed state, or a session header off the wire — so a correctly signed
manifest from an earlier transfer between the same operators is rejected.

## Threading

Nothing here is thread-safe on a single handle. Two threads may use two
different handles concurrently; two threads must not use the same handle without
their own synchronisation.

The error channel is thread-local, as above.

## Keeping the header honest

Three views of the ABI must agree: the Rust `extern "C"` surface, the committed
header, and the caller's declarations.
[`scripts/check_abi.sh`](../scripts/check_abi.sh) fails the build when they
drift, and it runs in the gate. Regenerate the header with
[`scripts/gen_header.sh`](../scripts/gen_header.sh) after any change to the Rust
surface, then bump `DHOW_ABI_VERSION`.

A stale header is the dangerous case: callers compile against it, so a stale one
means compiling against a signature that no longer exists.

## What binding this does not give you

The C ABI covers the codec and the crypto. It does **not** cover packing a
directory, extracting one safely, the archive format, or the CLI's behaviour —
those live in Go, in [`cli/internal/pack`](../cli/internal/pack).

A third-party receiver therefore has to implement extraction itself, including
re-validating every file name against the traversal rules in
[`proto/manifest.md`](../proto/manifest.md) even though the manifest was signed.
A signature says who produced the names, not that they are safe.
[`proto/README.md`](../proto/README.md) lists the steps in order, and
[`scripts/conformance_cli.py`](../scripts/conformance_cli.py) will check the
result.
